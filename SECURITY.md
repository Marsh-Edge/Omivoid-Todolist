# Security Policy

## Scope

Omivoid is a local-first application. It has no accounts, no servers, no
analytics and makes no network requests of any kind — all data lives in
IndexedDB on the device it was created on.

The security boundary is therefore **the machine the app runs on**, plus the
integrity of the downloaded installer.

| Area | Boundary |
| --- | --- |
| Desktop app | The local OS account, the Electron sandbox and the app's own hardening (CSP, Electron fuses, permission lockdown, request guard) |
| Web build | The browser origin it is served from and the browser profile's IndexedDB |
| Distribution | The GitHub Release assets and the published SHA-256 checksums |

## Reporting a vulnerability

Please **do not open a public issue** for a security problem.

Use GitHub's private vulnerability reporting:

**https://github.com/Marsh-Edge/Omivoid-Todolist/security/advisories/new**

If that is not available to you, open a regular issue that contains only a
short description of the class of the problem and a note that a private
report is needed — **without** exploit details or proof-of-concept code.

### What to include

- Affected version (the release tag, e.g. `v0.1.0`) and platform
- What an attacker could achieve, and what access they need
- Reproduction steps or a proof of concept
- Whether user data could be read, modified or exfiltrated

### What to expect

- An acknowledgement within **7 days**
- An assessment (severity, planned fix, whether a disclosure date is needed)
  within **14 days**
- A fix and a new release for confirmed issues; credit is offered in the
  release notes unless you prefer otherwise

## Hardening already in place

These are the measures shipped in release builds:

- **Strict hash-based CSP** served by the loopback static server: inline
  scripts are only allowed with a matching `sha256-` hash.
- **Electron fuses**: `RunAsNode` disabled, `NODE_OPTIONS` and `--inspect`
  injection disabled, ASAR integrity validation enabled, the app may only load
  code from inside `app.asar`.
- **Permission lockdown**: only OS notifications are granted; camera,
  microphone, geolocation and device permissions are denied.
- **Request guard**: in production every request that would leave the machine
  is cancelled and logged.
- **Navigation lockdown**: the renderer may not navigate away from its own
  loopback origin; popups and `<webview>` are blocked.
- **DevTools disabled** in production builds.
- **SHA-256 checksums** published with every release so downloads can be
  verified.

## Release binaries are unsigned

Release builds are **not** code-signed — no certificate was available at the
time of writing. As a result:

- Windows SmartScreen may show "Windows protected your PC" on first run.
  Choose **More info → Run anyway** if you trust the download.
- macOS Gatekeeper would refuse to open an unsigned `.app`.

Verify downloads with the published checksums instead:

```bash
# Linux / macOS
sha256sum -c SHA256SUMS.txt

# Windows PowerShell
Get-FileHash .\Omivoid-<version>-setup.exe -Algorithm SHA256
```

Compare the digest with the one in `SHA256SUMS.txt` from the same release.

## Out of scope

The following are **not** vulnerabilities:

- Data stored unencrypted in IndexedDB — this is inherent to a local-first app
  with no key management. Anyone with access to the OS account and the browser
  profile can read the data.
- The loopback renderer server having no authentication — any process running
  as the same OS user can reach it. This is an accepted, documented trade-off.
- Unsigned binaries (see above).
- Reports generated by automated scanners without a demonstrated impact.
